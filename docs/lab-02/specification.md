# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a Requester-facing ticketing MVP where a testing Requester identity (via a
Development Requester selector, not real login) can create an IT support ticket with
attachments, receive a system-generated Ticket Number, and locate, review, and manage
that ticket through a My Tickets list and a read-only Ticket Detail screen — establishing
the Zen Green UI foundation that later labs will reuse.

## 2. Stakeholder Request Interpretation
The IT department wants Requesters to self-serve: describe a problem, classify it, attach
evidence, and submit — then track it themselves without needing IT staff to look anything
up for them. Because real login isn't built yet, we simulate "being a specific Requester"
with a manual selector so multi-user ownership rules (a Requester only ever sees their own
tickets) can be built and proven now, ready to swap for real authentication in Lab 3.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only identity switch)
- Create Ticket (form, validation, attachment upload, Ticket Number generation)
- My Tickets (search, filter, sort, pagination, ownership-scoped)
- Requester Ticket Detail (read-only ticket fields + attachment management)
- Attachment lifecycle: upload, download, soft-remove
- Zen Green theme tokens as a shared, reusable style source

### Excluded
- Authentication, sessions, passwords, tokens, real authorization
- IT Staff dashboard, ticket ownership/assignment, IT Priority, status changes
- Public Comments, Internal Notes, Actions Taken
- Any status beyond `NEW` (no resolve/close/reopen)
- Administrator functions (user/category/related-system management)

## 4. Functional Requirements
- FR-01: The system shall generate a unique, backend-assigned Ticket Number when a Ticket is created.
- FR-02: The system shall let a Requester create a Ticket with Category, Related System, Summary, Description, Requested Priority, and 0–5 Attachments.
- FR-03: The system shall list Tickets belonging only to the currently selected Requester, with search, category/priority/status filters, sorting, and pagination.
- FR-04: The system shall retrieve one Ticket's detail only when it belongs to the currently selected Requester.
- FR-05: The system shall let a Requester add an Attachment to their own existing Ticket.
- FR-06: The system shall let a Requester soft-remove their own Attachment with a reason.
- FR-07: The system shall prevent download or preview of a soft-removed Attachment.
- FR-08: The system shall load only `active = true` Requesters into the Development Requester Selection screen.
- FR-09: The system shall persist the selected Requester across navigation until explicitly changed.
- FR-10: The system shall reload all Requester-scoped data whenever the selected Requester changes.

## 5. Business Rules

| ID | Rule |
|---|---|
| BR-01 | The official Ticket Number is generated by the backend and is unique. Format: `TKT-<year>-<id padded to 6 digits>` (e.g. `TKT-2026-000001`), derived from the Ticket's auto-increment `id` at creation time. Simple, guaranteed-unique, sortable, no extra sequence table needed. |
| BR-02 | A new Ticket always starts with `currentStatus = NEW`. No other status is reachable in Lab 2. |
| BR-03 | The Development Requester selector is a testing mechanism only, not authentication. The selected `requesterId` travels as an explicit request parameter and must never be treated as a verified identity. |
| BR-04 | `Ticket.createdAt`/`ticketDate` is set by the server at insert time, never accepted from the client. `Ticket Owner` (IT Staff assignment) is out of scope for Lab 2 and is not implemented. |
| BR-05 | The selected Requester is held in client-side state (React context, backed by `sessionStorage` so a page refresh doesn't lose it mid-session). Switching Requester clears all cached Requester-scoped data and re-fetches from the API — never reuse stale cached lists across a switch. |
| BR-06 | A Ticket's `requesterId` is set once, from the currently selected Requester, at creation, and is immutable afterward. |
| BR-07 | My Tickets defaults to `sort=createdAt&order=desc`. An invalid/missing `page`, `pageSize`, or `sort` value silently falls back to its default rather than returning a 400 — search/filter UX should never hard-error on a bad query string. |
| BR-08 | `summary`: required, 1–150 chars after trimming. `description`: required, 1–2000 chars after trimming. (Trim first, then validate length, so pure-whitespace input is treated as empty.) The Submit button is disabled for the duration of the request to prevent duplicate double-submission from repeated clicks. |
| BR-09 | If ticket creation fails (validation error or API/network failure), the form's entered values remain on screen unchanged so the Requester can fix the problem and resubmit without retyping. |
| BR-10 | Allowed attachment types: JPG/JPEG, PNG, WEBP, PDF. Max 5 MB/file, max 5 **active** attachments per Ticket (soft-removed ones don't count toward the limit). Removal is soft-remove only (`removedAt` + `removalReason`); a removed Attachment keeps its metadata visible but its download/preview endpoints return 404 once removed. If the Ticket itself saves successfully but an attachment upload fails, the Ticket is kept (attachments are not part of the same atomic transaction as ticket creation) — losing the whole ticket over one bad file would be worse for the Requester than a partial success with a clear error. |
| BR-11 | Inactive Requesters are excluded from the Selection dropdown **and** rejected server-side if a `requesterId` for an inactive Requester is somehow submitted (defense in depth, since the selector is not real auth). |
| BR-12 | Two distinct empty UI states: **Empty** = this Requester has zero Tickets ever (show a "Create your first ticket" CTA). **No results** = filters/search matched zero of N existing Tickets (show "Clear Filters" CTA). These must not share the same message. |
| BR-13 | `GET` single-Ticket and all Attachment actions verify `Ticket.requesterId === requestingRequesterId` server-side. On mismatch, respond `404 Not Found` (not `403`) so an unauthorized Requester can't even confirm the Ticket exists. |
| BR-14 | `RequesterUser.id` is designed to map 1:1 onto a future authenticated `User.id` in Lab 3. The only planned Lab 3 change is *how* `requesterId` is obtained (from a verified session/token instead of a client-supplied query parameter) — no Lab 2 data model change should be required. |

## 6. UI Specification Summary
Full detail lives in `docs/lab-02/ui-spec.md` (separate deliverable, same PR). Summary: a
persistent nav shell (TokTickIT title, My Tickets / Create Ticket links, current-Requester
display, active-page indicator, responsive mobile nav) wraps three main screens — Create
Ticket, My Tickets, Ticket Detail — plus the Development Requester Selection screen shown
before the shell. All screens share Zen Green tokens (§7 of the labsheet), a single badge
component for Requested Priority/Current Status, and consistent loading / empty /
no-results / error / validation states.

## 7. Data Changes

**New models** (Prisma), added to the existing Lab 1 schema — `Category` from Lab 1 is
reused unmodified (no `active` flag: the stakeholder never asked for category
deactivation, so adding one now would be unjustified scope):

```prisma
model RequesterUser {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  active    Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

model RelatedSystem {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  active    Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

enum Priority {
  LOW
  MEDIUM
  HIGH
}

enum TicketStatus {
  NEW
  OPEN
  IN_PROGRESS
  RESOLVED
  CLOSED
  // Only NEW is reachable in Lab 2; the rest exist now so Lab 3/4
  // don't need another migration just to add status values.
}

model Ticket {
  id                Int          @id @default(autoincrement())
  ticketNumber      String       @unique
  requesterId       Int
  requester         RequesterUser @relation(fields: [requesterId], references: [id])
  categoryId        Int
  category          Category     @relation(fields: [categoryId], references: [id])
  relatedSystemId   Int
  relatedSystem     RelatedSystem @relation(fields: [relatedSystemId], references: [id])
  summary           String
  description       String
  requestedPriority Priority
  currentStatus     TicketStatus @default(NEW)
  createdAt         DateTime     @default(now())
  updatedAt         DateTime     @updatedAt
  attachments       Attachment[]

  @@index([requesterId])
  @@index([categoryId])
  @@index([currentStatus])
  @@index([createdAt])
}

model Attachment {
  id             Int       @id @default(autoincrement())
  ticketId       Int
  ticket         Ticket    @relation(fields: [ticketId], references: [id])
  originalName   String
  storedFilename String
  mimeType       String
  sizeBytes      Int
  uploadedAt     DateTime  @default(now())
  removedAt      DateTime?
  removalReason  String?

  @@index([ticketId])
}
```
(`Category` from Lab 1 gains a `tickets Ticket[]` back-relation field — the only edit needed to the existing model.)

**Indexes justified:** `requesterId`, `categoryId`, `currentStatus`, `createdAt` are indexed
because My Tickets filters/sorts on all four directly (§6.1 of the labsheet) — without
these, every list query would be a full table scan.

## 8. API Contract

All Requester-scoped endpoints take `requesterId` as a query parameter (per BR-03/BR-13 —
explicitly *not* secure, documented as the Lab 2 testing mechanism).

| Method & Path | Purpose | Success | Key errors |
|---|---|---|---|
| `GET /api/requesters` | Active Requesters for the selector | 200, `[{id,name}]` | 500 |
| `GET /api/related-systems` | Active Related Systems | 200, `[{id,name}]` | 500 |
| `GET /api/categories` | Categories (reused from Lab 1) | 200, `[{id,name}]` | 500 |
| `POST /api/tickets` | Create a Ticket | 201, full Ticket incl. `ticketNumber` | 400 validation, 500 |
| `GET /api/tickets?requesterId=&search=&category=&requestedPriority=&status=&sort=&order=&page=&pageSize=` | Paginated, owned ticket list | 200, `{ data:[...], page, pageSize, total, totalPages }` | 400 missing requesterId |
| `GET /api/tickets/:id?requesterId=` | One owned Ticket + its active Attachments | 200 | 404 not owned/not found |
| `POST /api/tickets/:id/attachments?requesterId=` | Upload one Attachment (multipart) | 201, Attachment metadata | 400 invalid type/size, 404 not owned, 409 already 5 active attachments |
| `GET /api/attachments/:id` | Attachment metadata (works even if soft-removed — metadata must stay visible) | 200, metadata | 404 not owned/not found |
| `GET /api/attachments/:id/download?requesterId=` | Download an **active** Attachment | 200, file stream | 404 removed/not owned/not found |
| `DELETE /api/attachments/:id?requesterId=` body `{ reason }` | Soft-remove an Attachment | 200, updated metadata | 400 missing reason, 404 not owned/not found |

**Search:** matches `ticketNumber` OR `summary`, case-insensitive substring (matches the
"Search by ticket number or summary…" placeholder in the approved My Tickets mockup).
**Sort fields:** `createdAt` (default), `ticketNumber`, `requestedPriority`, `currentStatus`.
**Pagination:** `page` default 1, `pageSize` default 10 (max 50) — out-of-range values clamp rather than error (BR-07).

## 9. Acceptance Criteria
- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed. *(FR-01, FR-02)*
- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets or Create Ticket, then the Requester Selection screen is shown instead. *(BR-05)*
- AC-03: Given Requester B is selected, when a Ticket or an Attachment belonging to Requester A is requested by ID — via ticket detail, attachment metadata, attachment download, or attachment removal — then a 404 is returned and no data is returned or modified. *(BR-13)*
- AC-04: Given the Summary field is empty, when the Requester submits, then a field-level error appears below Summary and no API call is made. *(BR-08)*
- AC-05: Given an in-flight submission, when the Requester clicks Submit again, then the button is disabled and no duplicate Ticket is created. *(BR-08)*
- AC-06: Given the backend is unreachable, when the Requester submits a valid form, then a safe error message is shown and all entered field values remain. *(BR-09)*
- AC-07: Given a Requester with zero Tickets, when they open My Tickets, then the Empty state (not No-results) is shown with a Create Ticket CTA. *(BR-12)*
- AC-08: Given a Requester with Tickets but an active filter matching none of them, when My Tickets loads, then the No-results state is shown with a Clear Filters CTA. *(BR-12)*
- AC-09: Given more Tickets than one page, when the Requester changes page, then only that page's Tickets load without losing the active search/filter/sort. *(FR-03)*
- AC-10: Given Requester A is viewing My Tickets, when they switch to Requester B via Change Requester, then Requester A's Tickets no longer appear and Requester B's Tickets load fresh. *(FR-10, BR-05)*
- AC-11: Given a valid JPG under 5 MB, when the Requester attaches it during creation, then it uploads and appears listed on the created Ticket. *(BR-10)*
- AC-12: Given a .exe file, when the Requester attempts to attach it, then it is rejected client-side with a clear message and never reaches the API. *(BR-10)*
- AC-13: Given a Ticket already has 5 active Attachments, when a 6th is attempted, then the upload is rejected with a clear message. *(BR-10)*
- AC-14: Given an owned Attachment, when the Requester soft-removes it with a reason, then it still appears in the list as removed metadata but its download link is disabled. *(BR-10)*
- AC-15: Given a removed Attachment, when a download is attempted via direct API call, then the server returns 404. *(BR-10)*
- AC-16: Given no active Requesters exist, when the Selection screen loads, then a safe empty state is shown instead of a blank dropdown. *(FR-08)*
- AC-17: Given the Requesters API fails, when the Selection screen loads, then a safe error state is shown instead of a crash or infinite spinner. *(FR-08)*
- AC-18: Given the viewport is under 768px, when any of the three main screens render, then no horizontal scrolling occurs and all controls remain reachable. *(§8.7)*
- AC-19: Given a search term that matches a Ticket's `summary` or `ticketNumber` (case-insensitive substring), when My Tickets loads with that search term, then only matching Tickets are returned. *(FR-03)*
- AC-20: Given a `categoryId`, `requestedPriority`, or `status` filter value, when My Tickets loads with that filter applied, then only Tickets matching the filter value are returned. *(FR-03)*
- AC-21: Given a `sort` field and `order` direction, when My Tickets loads with those parameters, then the returned Tickets are ordered accordingly. *(FR-03, BR-07)*
- AC-22: Given a field fails validation, when the error message renders, then the field's input is associated to that message via `aria-describedby`. *(§12 Accessibility)*

## 11. Assumptions and Decisions
- **Ticket Number = `TKT-<year>-<id padded 6>`** — simplest unique/sortable scheme; revisit only if the course later requires per-year reset numbering.
- **`requesterId` passed as a query parameter**, not a header — explicit, easy to test with Supertest, and honestly documents that this is *not* real auth (a header might look more "secure" than it actually is).
- **404, not 403, for cross-Requester access** — avoids confirming a Ticket's existence to someone who shouldn't see it.
- **Category has no `active` flag** — Lab 1's schema is reused as-is; only `RequesterUser` and `RelatedSystem` get `active` per the explicit Lab 2 requirement.
- **Attachment upload failure does not roll back Ticket creation** — treated as two separate, independently-recoverable operations rather than one all-or-nothing transaction.
- **Selected Requester stored in `sessionStorage`**, not `localStorage` — intentionally resets between browser sessions so it doesn't linger like a fake "remembered login."
- **No separate confirmation modal before soft-remove.** The required `reason` field itself
  is the confirmation step — a Requester must consciously type a reason before the DELETE
  request fires, which is enough friction to prevent accidental removal without adding a
  second "Are you sure?" dialog on top of it.
- **No in-app attachment preview in Lab 2** (no image lightbox or PDF viewer). Only
  download is supported. The stakeholder's requirement ("inspect attachments") is
  satisfied by download; in-app preview is unrequested extra scope.
- **Ticket-list query parameter renamed `category` → `categoryId`** in `api-spec.md` §4,
  to match the `categoryId` field name already used in the `POST /api/tickets` body
  (§8) — avoids ambiguity about whether the filter takes a category name or an id (it's
  always an id).
- **Seed data will match the labsheet minimums exactly**, not over-seed: 6 Related
  Systems, 4 active + 1 inactive Development Requester. Fixed, known counts make
  pagination and "no active Requesters" test fixtures predictable in Phase 2 onward.
